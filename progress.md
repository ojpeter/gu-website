**Previous resume note (superseded, kept for context):** **Dark/light theme built site-wide, done and verified.** `requirements.md` Section 9 had explicitly deferred this to "Phase 3+, evaluate once light-mode is solid" — superseded today by direct client instruction ("Apply dark and light themes throughout the website"), both `requirements.md` (Section 9 bullet + Section 21 roadmap row) updated to record the supersession rather than silently contradicting the written plan. Because every color in `style.css` already routed through CSS custom properties (or a component's own intentionally-permanent dark background — `.hero`/`.cta-banner`/`.slide-visual--brand`/`.site-footer`, all correctly left untouched), this was a genuinely small, low-risk addition rather than a redesign:
- **New/changed tokens, dark values only**: `--gu-ink`/`--gu-body`/`--gu-muted`/`--gu-border`/`--gu-surface`/`--gu-surface-alt`/`--gu-surface-tint` (neutrals), `--gu-green-deep`/`--gu-green-dark`/`--gu-red-deep` (brightened — the light-mode "deep" accents, used as TEXT color in ~20 places, would fail contrast against a near-black surface unchanged), plus three new tokens introduced to eliminate the last few hardcoded hex values standing in the way (`--gu-header-bg`, `--gu-badge-yellow-bg`/`-fg`, `--gu-badge-red-bg`), and dark-appropriate `--gu-shadow`/`--gu-shadow-lg`/`--gu-shadow-card-hover` (black shadows barely read on a dark surface; the light green "glow" shadow is kept but strengthened since glows read well on dark backgrounds). Brand colors (`--gu-green`/`--gu-yellow`/`--gu-red` themselves) are unchanged in both themes per Section 3.5 — only the neutrals and the two text-role "deep" accents needed a dark variant.
- **Two ways in, standard pattern**: `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { ... } }` for the OS-level default, and `:root[data-theme="dark"] { ... }` (identical values) for an explicit toggle that always wins regardless of OS setting. A header toggle button (`#theme-toggle`, sun/moon icons that cross-fade/rotate depending on which theme is active) sets `data-theme` on `<html>` and persists the choice to `localStorage` (`assets/js/main.js`). An inline `<script>` in `<head>` (`layout_header.php`, before the stylesheet link) applies any stored explicit choice before first paint — the standard anti-FOUC technique, deliberately not deferred to `main.js` which loads at the end of body, long after first paint. Noted in a code comment: this inline script will need a nonce if/when Rule 5's CSP header is actually implemented (not yet built — confirmed via grep, still just a documented requirement).
- **Contrast verified programmatically, not eyeballed** (Rule 6): computed real WCAG relative-luminance ratios for every new dark-mode text/background pairing via a small Node script — headings 16.57:1, body text 11.92:1, muted text 7.30:1 (6.70:1 against the alt surface), the two brightened green accents 9.55:1/8.09:1, brightened red 6.78:1 — all comfortably clear AA (4.5:1), most clear AAA (7:1). Checked the dark border's non-text contrast too (1.34:1) — initially looked too subtle against the 3:1 guideline for UI-component boundaries, but computing the *existing, already-shipped* light-mode border-vs-white-surface ratio found it's **also** only 1.25:1 — this is a pre-existing hairline-border characteristic of the whole design system (real depth cues come from `box-shadow`, not the border), so dark mode intentionally matches that same subtlety rather than introducing an inconsistent, more prominent border that the light theme itself doesn't have.

## The 11 Rules (mirrored from `CLAUDE.md` — self-contained per Rule 11)

1. **This is a full build, not a brochure site** — every content area (Academics, Admissions, Research, News & Events, Community Engagement, Careers, Press/Media, Search, Contact/Directory, eServices directory) is a real CMS-managed feature with its own data model, not a static page. `gu-services` handles transactional/authenticated systems; this project owns 100% of the public/marketing/informational experience, built out fully.
2. **Rate limiting** — every input-accepting/costly route (contact, newsletter, concern-report, search, admin login/password-reset, exports) via a DB-backed limiter, logged on violation.
3. **Query design & optimization** — PDO prepared statements via `db()` always; index FK/WHERE/ORDER BY/JOIN columns; no N+1 (explicit JOINs); server-side pagination everywhere; no migration tool, but every schema change checked into `database/schema_*.sql`.
4. **Form input validation** — one shared `Validator` class, enforced server-side regardless of client JS; real dates, real file-upload MIME re-validation via `finfo`, enum fields validated against real lookups, forms re-populate on failure.
5. **SQL injection / XSS / CSRF / core security** — prepared statements everywhere; `esc()` on all output including CMS content; CSRF tokens on every state-changing form; bcrypt/argon2 + session regeneration + **mandatory 2FA for Content Approver/Administrator**; explicit role checks server-side; secure session cookies via `start_secure_session()`; explicit INSERT/UPDATE column whitelists; append-only audit log on every admin publish/edit/delete; no stack traces/DB errors exposed; no Composer dependencies by default; CSP/security headers/HSTS set deliberately; `security.txt` published before launch.
6. **Accessibility (WCAG 2.2 AA), non-negotiable** — semantic HTML/ARIA/keyboard operability/skip links from the first template built; alt text a required CMS field; contrast-verified design tokens (yellow accent = dark text only); `prefers-reduced-motion` respected; automated + manual (screen reader/keyboard) testing; a real, maintained Accessibility Statement page.
7. **Performance & SEO are load-bearing** — Core Web Vitals budget (LCP<2.5s, INP<200ms, CLS<0.1) on 4G mobile; responsive/modern-format images, lazy-loading, cache-busted assets; semantic URLs, schema.org structured data, sitemap, deliberate `robots.txt`; caching for high-traffic low-change pages.
8. **CMS & editorial roles, own model** — Content Editor / Content Approver / Administrator, a small purpose-built role set — never reuse or gain access to `gu-services`'s 28-role HR/DMS/EVoting RBAC core. Every content type has full revision history, scheduled publishing, and a visible "as of [date]" stamp on data-driven content. Event de-duplication enforced in-schema (fixes the current live site's duplicate "Mature Age Entry Exams" bug). Never publish a placeholder statistic — omit unverified facts instead of showing "0".
9. **The `gu-services` integration is phased: static link first, live bridge later** — Phase 1 needs only one config-driven "eServices" link (`ESERVICES_URL` env value: `http://localhost/gu-services` dev / `https://eservices.gu.ac.ug` prod), pointing at `gu-services`'s own Portal landing page. A live, per-system directory built into the website (via a narrow, isolated, read-only bridge module whitelisted to the `systems` catalog, working-calendar data, public vacancy rows, public GU-DMS documents) is explicitly deferred to Phase 2+. Whenever built, that bridge never writes to `gu-services`'s DB and never touches its RBAC/employee/student tables, and is in scope for every security review.
10. **Data protection (Uganda DPPA 2019)** — no personal-data-collecting feature ships without a stated lawful basis + retention period recorded in `requirements.md` Section 14's data-flow table; real, technically-enforced cookie/analytics consent; the "Report a Concern" channel gets disproportionate care (elevated storage protection, restricted access, defined handling process); the public staff directory only ever exposes a small curated table, never HR's confidential schema.
11. **`progress.md` (this file), mandatory every session** — read before starting, updated before ending, every session. Must contain: this rules copy, a dated completed-tasks log, a pending/in-progress list by phase, known issues/open questions, a top "resume here" note, and cross-project notes relevant to `gu-services`.
